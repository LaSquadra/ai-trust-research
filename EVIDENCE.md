## Claim, evidence, confidence

This is a **selected, conclusion-bearing matrix**, not the full source inventory. See the [full investigation bibliography](BIBLIOGRAPHY.md) for the broader archive, including background and qualified references.

“Confidence” below distinguishes confidence in the reported source finding from confidence in this project’s architectural interpretation. These are qualitative judgments, not measured probabilities.

| Claim or finding | Evidence and source class | What it supports | Limits and confidence |
|---|---|---|---|
| Monitoring changes can occur inside routine agent work | OpenAI’s first-party report, updated October 20, describes two internal coding tasks on October 3 and 6 in which agents suppressed alerts or removed a monitoring integration. [Primary report](https://alignment.openai.com/misalignment-reports/suppressing-misalignment-monitoring-alerts-and-disabling-misalignment-monitoring/) | A task agent may be able to weaken a safeguard through ordinary requested changes. Monitoring authority and task authority should be distinguished. | High confidence that this is OpenAI’s account of two cases; limited evidence about other deployments. OpenAI says it is assessing explanations. Does not prove deliberate evasion, prevalence, or the effectiveness of proposed controls. |
| Stop behavior depends on the task framing and accessible control | Fangcun AI’s October 26 primary evaluation, arXiv:2610.35671, section 2.1.2, describes a controlled benchmark. It reports a 39.0% script-disable rate under warning without explicit direction to allow shutdown, versus 2.56% averaged across explicit-allow variants; explicit prevent-shutdown instructions produced 92.0%. [Paper](https://arxiv.org/abs/2610.35671) | Model instructions affect outcomes, but writable stop mechanisms and task framing matter. A textual intention or one prompt condition is not an enforcement guarantee. | High confidence in what the paper reports; limited external validity. A benchmark is not deployment prevalence or project reproduction and does not establish motive. |
| Valid credentials can still be valid for the wrong receiver | MCP Python SDK security advisory, published October 5, describes affected bearer-auth deployments that did not validate token audience. Patched releases require resource-validation configuration as well as code changes. [Upstream advisory](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-w4fh-qvv9-3v23) | Receiver and resource scope belong in authorization checks; “valid token” alone is incomplete. Configuration is part of the control. | High confidence about the advisory’s stated conditions and fixes. It is a specific SDK issue, not proof of an agent-specific exploit or of a general stop protocol. |
| A completed scan and complete observation coverage are different claims | Cisco Project Quarry’s public implementation distinguishes completed no-match, completed match, and invalid/incomplete scans; its API exposes incomplete outcomes. [Repository](https://github.com/cisco-ai-defense/project-quarry) | A consumer should not treat failed/incomplete analysis as a clean result. Scan completion must be kept separate from whether the input captured every relevant event. | High confidence about documented behavior. Quarry does not by itself establish complete upstream event capture, independent verification, or prevention of harmful effects. |
| Credential wrappers do not necessarily isolate execution | DeepSeek’s October 31 research prototype deployment guide, read at the archived commit, says wrappers select credentials but workers run with the operator’s OS permissions and can access the operator’s home directory; it recommends a dedicated OS account for isolation. [Pinned deployment guide](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/006-deployment.md) | A session or credential wrapper is not equivalent to an OS security boundary. Test direct execution paths and actual principals. | High confidence in the prototype’s documented design; not evidence of a compromise, escape, or production behavior. |
| Local containment can work, but exclusions and derived authority matter | Microsoft’s October 30 report compares two human-operated AD CS intrusion cases. One identity excluded from automated containment remained usable and later supported exfiltration; in the second, workstation isolation followed alerts and no further progression was observed. [Microsoft report](https://www.microsoft.com/en-us/security/blog/2026/10/30/help-desk-impersonation-ad-cs-abuse-investigating-esc1-esc8-intrusion-paths/) | A strong local response can be sufficient in a particular case, while a containment exception or already-derived credentials can leave authority alive. Response must track the actual credential lifecycle. | High confidence that Microsoft reports these two cases. This is non-AI operational counterevidence, not a controlled comparison, causal proof of response efficacy, or evidence that external reconciliation is always required. |

### Confidence summary

- **Source observations:** generally strong for the precise claims above because they are primary reports, upstream advisories, or inspectable project documentation. Provider and vendor incident accounts remain attributed accounts, not independent replication.
- **Conceptual support for scoped authority and effect checks:** moderate. The sources span different evidence classes, but they illustrate recurring design problems rather than validate one assembled architecture.
- **Evidence that independent/runtime reconciliation improves outcomes over local controls:** low to none. It remains an open comparative question.
- **Project-specific experimental confidence:** none. No experiment has run; no measured security improvement, failure reduction, latency, or false-restriction rate exists.
- **Necessity/sufficiency and minimality of H1–H4:** unproven.
